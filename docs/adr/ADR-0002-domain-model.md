# ADR-0002: Relational Domain Model and pgvector Persistence

- **Status:** Accepted
- **Date:** 2026-08-10
- **Authors:** Ayush Mehta

---

## Context

Intellery requires a robust persistence layer capable of supporting:
1. Relational data with strict referential integrity (Users, Events, Roles, Photos, Upload batches).
2. Complex multi-table entity hierarchies (Events $\rightarrow$ Photos $\rightarrow$ DetectedFaces $\rightarrow$ FaceVectors).
3. Event-scoped face clustering (`Identity`) where faces belonging to the same individual across multiple photos in an event are grouped together.
4. User identity auto-resolution mapping an attendee's registration selfie to an event-specific face cluster (`UserIdentity`).
5. High-dimensional vector storage and approximate nearest neighbor (ANN) similarity search for both 512-D face recognition embeddings (ArcFace) and 512-D scene semantics embeddings (OpenAI CLIP).

We evaluated whether to use a dedicated external vector database (such as Milvus, Qdrant, or Pinecone) alongside PostgreSQL, or to leverage PostgreSQL with the `pgvector` extension.

---

## Decision

We decided to use **PostgreSQL 16** with the **`pgvector`** extension as the single source of truth for both relational application data and high-dimensional vector embeddings, managed via **Prisma 7**.

### Core Schema Models

```
User (id, email, passwordHash, displayName, selfieKey)
  │ 1:1
  ├──► UserFaceVector (vector(512), model: W600K_R50)
  │
  ├──► EventMember (role: ADMIN | CONTRIBUTOR | VIEWER) ◄──┐
  │                                                         │
  └──► Upload (status: PENDING | PROCESSING | COMPLETED)    │
         │ 1:N                                              │
         ▼                                                  │
       Photo (storageKey, status: PENDING | COMPLETED)      │
         ├── 1:1 ──► PhotoAnnotation (vector(512), CLIP)    │
         └── 1:N ──► DetectedFace (bbox, 5-landmarks)       │
                       │ 1:1                                │
                       ├──► FaceVector (vector(512))        │
                       │                                    │
                       └──► Identity (displayName) ◄────────┤ (Scoped to Event)
                              ▲                             │
                              │ 1:1                         │
                              └── UserIdentity ─────────────┘
                                  (userId, eventId, identityId)
```

1. **Face Embeddings (`FaceVector`):**
   Defined with column type `Unsupported("vector(512)")`. Embeddings are generated by the ArcFace ResNet-50 backbone and represent facial identity.
2. **Scene Embeddings (`PhotoAnnotation`):**
   Defined with column type `Unsupported("vector(512)")`. Embeddings are generated by OpenAI CLIP ViT-B/32 and represent holistic photo composition and visual concepts.
3. **Event Identity Scoping (`Identity` & `UserIdentity`):**
   Identities are strictly scoped to an `eventId`. When a user joins an event, their selfie embedding is compared against the event's face vectors. If a match is verified above threshold $0.55$, a `UserIdentity` record is created linking `(userId, eventId)` to `identityId`.

---

## Rationale & Benefits

1. **Transactional Integrity & ACID Guarantees:**
   Face detections, facial landmark metadata, identity links, and embeddings are committed within transactional boundaries. If an upload or worker job fails, database state remains consistent without orphan vector records.
2. **Elimination of Dual-Store Synchronization:**
   Maintaining a separate vector database requires synchronization mechanisms, distributed transactions, and custom failure handling when vector operations succeed but metadata operations fail. `pgvector` eliminates this entire failure domain.
3. **Unified Query Expressiveness:**
   PostgreSQL enables hybrid queries in a single SQL statement: filtering by `eventId`, joining on `DetectedFace` and `Identity`, and ordering by cosine distance (`<=>`) using indexes.

---

## Consequences

### Positive
- Single database technology to deploy, back up, and monitor.
- Zero network hops between metadata lookups and vector distance computations.
- Prisma client handles migrations and strong typing for all non-vector attributes, while raw queries (`$queryRaw`) handle optimized vector math.

### Negative / Trade-offs
- High memory usage: PostgreSQL buffer pool and vector index RAM requirements grow with millions of vectors.
- HNSW or IVFFlat index tuning is required as datasets scale beyond tens of thousands of event photos.
